# ADR-0041 — Headless screenshots: a scene catalogue, rendered by the app, never committed

- **Status:** Accepted (owner, 2026-11-11; S1–S8 proposed by Claude and approved, S3 changed by the
  owner from light to dark)
- **Date:** 2026-11-11
- **Implements:** ADR-0009 §6 (screenshots generated headless by the app itself, en-US, shared by
  both guides), ADR-0012 (headless rendering with our own renderer), ADR-0039 D8 (PNG encoding
  arrives with the screenshots), ADR-0036 B7 (the `miniz_oxide` duplicate). Step F2.05 of
  SCALETTA.
- **Amends:** ADR-0014 §7 and ADR-0037 T10 (§7): the guides' screenshots use **Studio's dark
  half**, no longer the light one (S3).

## Context

ADR-0009 §6 says the guides' screenshots are generated headless by the program itself, but not
how, where they go or whether they are committed. F2.03 gave us a renderer that draws a display
list into an in-memory image (ADR-0039 D8), and F2.04a a view (the demonstration window of
ADR-0040 W8) behind the `WindowApp` trait. What was missing: PNG encoding, a program that renders
views without a window, the `cargo xtask screenshots` command, and the rules every future
screenshot follows. These rules are worth an ADR because every guide chapter will depend on them.

Facts checked on 2026-11-11: `xtask` is dependency-free (std only) by design, so it cannot draw;
`tiny-skia` 0.12's `png-format` feature brings `png` 0.18.1 (MIT OR Apache-2.0, the latest on
crates.io), which uses `miniz_oxide` 0.8 directly and 0.9 through `flate2`, as ADR-0036 B7
foresaw; the guides compile with Typst with the repository as root.

## Decision

### S1 — A developer binary in `orchestra-app`

`orchestra-app` becomes a library plus two binaries: `orchestra` (the program users run) and
`orchestra-screenshots <OUT_DIR>` (a developer tool, **never distributed**). The views live in the
library, so both binaries draw the very same code; `cargo xtask screenshots` runs the tool with
`cargo run`. The tool's messages are English, for developers, like `xtask`'s.

### S2 — A catalogue of scenes

Every screenshot is one entry of `orchestra_app::SCENES`: a kebab-case name (the file name), a
logical size and a function that records the view in the state to show (the view's `layout`,
then any input events, e.g. to place the pointer). Adding a picture to the guides means adding an
entry. Today the only scene is `demo-window`, the demonstration window at rest.

### S3 — Fixed theme, language and scale (owner: dark)

- **Theme:** Studio's **dark half**, set explicitly, never read from the system. Chosen by the
  owner on 2026-11-11 instead of the light half that ADR-0014 §7 and ADR-0037 T10 prescribed. A
  guide section that explains the themes may add light examples.
- **Language:** en-US, once the interface has text (F2.07), as ADR-0009 §6 already says.
- **Scale:** 2 device pixels per logical pixel: a 640-pixel-wide scene prints at about 200 dpi
  across the text width of an A4 page, and the high-DPI path is exercised.

### S4 — Not committed: `dist/screenshots/`, rebuilt by `cargo xtask guides`

The PNG files go to `dist/screenshots/` (ignored by git), for the same reasons ADR-0009 §4 gives
for the PDFs: no binary churn in the history, no stale pictures. `cargo xtask screenshots` deletes
the `.png` files already there first, so a removed or renamed scene leaves nothing behind.
`cargo xtask guides` runs `screenshots` before Typst, so a guide always shows the current code;
the guides include `/dist/screenshots/<name>.png`. The CI `guides` job therefore builds
`orchestra-app` too, and publishes the screenshots as an artifact next to the PDFs.

### S5 — Generated on Linux; checked in memory everywhere

The guides' files are generated by the CI `guides` job, on Linux. Pixel-identical output across
platforms is **not** required: with the `simd` feature `tiny-skia` runs different code on x86
and ARM, and the guides gain nothing from the guarantee. On all three platforms, ordinary tests
render every scene in memory and check its size, that it is fully opaque, that it encodes as PNG,
that two renders are identical and that it uses the dark theme. No comparison with reference
images for now: the only scene is a throw-away view without text; the question comes back with
the real views.

### S6 — PNG encoding in `orchestra-ui`

`Image::encode_png` uses `tiny-skia`'s encoder (8-bit RGBA, straight alpha); a failure is the new
`DrawError::PngEncoding`. Opaque images survive the round trip byte for byte (tested).
`miniz_oxide` 0.8 joins `skip` in `deny.toml` with its exit (a new `png`).

### S7 — The guides do not show the demonstration window

The guides keep their placeholders: the demonstration window is not something the reader will
ever use, so showing it would mislead. The first real screenshots arrive with the real views (at
the latest F2.15). F2.05 therefore changes nothing a user sees (`User-visible: no`).

### S8 — Amendments

ADR-0014 §7 and ADR-0037 T10 (§7) are amended as S3 says; both stay Accepted, with a note
pointing here.

## Alternatives rejected

- **A hidden `--screenshots` option in `orchestra`:** developer code and messages inside the
  program users run, and messages a user could see would have to be translated.
- **Committed PNG files (e.g. `assets/screenshots/`):** faster guide builds, but binary churn and
  pictures that can silently fall behind the code.
- **Pixel-identical screenshots on every platform:** costs (no `simd`, or our own rasteriser
  rules) with no benefit for the guides.
- **Reference-image tests now:** they would freeze a throw-away view; reconsidered with the real
  views.

## Consequences

- The `guides` CI job takes a few minutes more (it builds `orchestra-app`); its timeout grows
  from 20 to 30 minutes.
- Seven small crates (eight packages, `miniz_oxide` twice) enter the build of `orchestra-ui`:
  `png`, `flate2`, `miniz_oxide`, `fdeflate`, `crc32fast`, `simd-adler32`, `adler2`, all under
  MIT, Apache-2.0, Zlib or 0BSD licences (accepted by `deny.toml`). No native library.
- Every future view that the guides show adds one entry to `SCENES`.
